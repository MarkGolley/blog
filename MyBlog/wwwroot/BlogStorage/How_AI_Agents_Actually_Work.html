Part 1

What agents are doing

First, separate the machinery from the behaviour. An agent is useful because it can loop through work, not because it gives one impressive answer.

The simplest useful definition

My current definition is: an AI agent is a model inside a loop, connected to tools, with enough instructions to decide what to do next.

That loop is the shift. A normal chatbot can answer from the context you paste in. An agent can inspect the environment, make a change, run a check, learn from the result, and decide whether the work is done.

The model is not the whole agent

It is easy to talk about agents as if the model itself is doing everything. Really, the model is only one part of the system around it. I find it clearer to separate the parts from the path the work takes.

The main parts are:

  • Model: reasons over the available context and proposes the next action.
  • Runtime: manages the loop: context, tool calls, approvals, retries, memory, and stopping conditions.
  • Tools: expose real capabilities such as files, shell commands, browsers, APIs, tests, docs, or databases.
  • Policy: decides what the agent can do automatically and what needs human approval.
  • Verification: checks whether the work should be trusted.

The diagram below is the same idea from a different angle. It shows one pass through the loop: a goal and instructions become context for the model; the model chooses a possible action; the runtime checks policy; a tool runs; the result comes back as an observation; then the agent either verifies the work or loops again.

That is why two agents can use the same model and still behave differently. It is also why repeatability is not guaranteed even with the same agent setup. Unless the model call, settings, context, tool outputs, runtime behaviour, and external state are all fixed, the next run may make a different choice or produce a different result.

This matters when something goes wrong. The fix is not always "write a better prompt". Sometimes the tool output was unclear. Sometimes the context was stale. Sometimes the runtime allowed too much access. Sometimes there was no test step. Sometimes the model just made a bad assumption and then built on it.

Practical guardrails How to reduce those failure modes.
  • Unclear tool output: ask for short, explicit command results and check the evidence yourself.
  • Stale context: have the agent re-read the relevant files, docs, or external state before acting.
  • Too much access: keep permissions narrow and require approval for risky actions.
  • No verification: ask what test, screenshot, log, or check proves the work.
  • Bad early assumption: use small plans and review points before letting the agent continue.

Context and tools decide what the agent can actually do

The model does not know your repo, product, database, or browser state in the way you do. It sees whatever the runtime gives it, plus whatever it actively gathers through tools.

At a high level, context can include the user request, platform instructions, project rules such as AGENTS.md, opened files, search results, tool outputs, previous reasoning, and summaries. If the important fact is not in that context, the model is guessing.

Tools usually come from a few places:

  • Built-in platform tools: file reading, editing, terminal access, browser automation, image viewing, or web search.
  • Local machine tools: installed programs such as dotnet, git, npm, rg, or test runners.
  • Project scripts: commands like run_checks.ps1, build tasks, lint tasks, seed scripts, or deployment helpers.
  • Connectors and MCP servers: integrations for GitHub, Slack, Jira, databases, browsers, internal docs, or custom systems.
  • Custom application tools: functions with explicit input and output schemas registered with the runtime.

The runtime describes those tools to the model. The model requests a tool call. The runtime executes it and returns the result. That boundary is important: a tool description is part of the contract, and bad tool output can become bad reasoning in the next loop.

The agent does not directly know that the world changed. It sees observations. If a command fails silently, a search result is stale, a test runner reports only part of the failure, or the agent misreads a diff, the next decision can be built on weak evidence. That is why good agent workflows make tool output short, explicit, and easy to verify.

Optional deep dive A simple tool schema and why MCP matters.

A tool exposed to an agent might look conceptually like this:

{
  "name": "search_blog_posts",
  "description": "Search published blog post HTML files by keyword.",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "The keyword or phrase to search for."
      },
      "maxResults": {
        "type": "integer",
        "description": "Maximum number of matching posts to return."
      }
    },
    "required": ["query"]
  }
}

If that description is vague, the model may call the wrong tool or pass weak arguments. If the tool fails but returns something that looks valid, the model may treat the result as truth.

MCP, or Model Context Protocol, is one way to standardise this boundary. In plain English, it gives agent runtimes a common way to discover and call external tools or data sources: GitHub, internal docs, browsers, databases, tickets, health checks, and more. That is powerful because it turns private systems into agent-usable capabilities. It is risky for the same reason, so permissions, audit logs, validation, and failure modes matter.

A small example makes the difference clearer

If I ask a chatbot, Why is my test failing?, it can answer from whatever error message I paste in.

If I ask an agent inside a codebase, it can do more:

  1. Read the failing test output.
  2. Open the test file.
  3. Find the production code being exercised.
  4. Compare the assertion with the current behaviour.
  5. Make a small change.
  6. Run the targeted test again.
  7. Summarise what changed and what risk remains.

That is a different workflow. The value is not just that the agent writes code. The value is that it can move between observation and action, then check whether the action worked.

What you are watching when an agent runs

A lot of agent behaviour looks strange until you map it back to the loop. When an agent reads files before editing, it is building context. When it asks for approval, it has reached a policy boundary. When it runs a test after a small change, it is trying to turn a guess into evidence.

The common visible steps usually mean:

  • File reads: the agent is collecting the facts it was not given in the prompt.
  • Searches: it is trying to find ownership, examples, naming patterns, or the exact failure surface.
  • Plans: it is stating a temporary hypothesis. A plan is useful, but it is not proof.
  • Permission prompts: the runtime is enforcing a boundary before a higher-risk action.
  • Tool calls: the agent is observing or changing external state through a controlled interface.
  • Diffs: this is the moment to check scope. The changed files should match the stated task.
  • Tests and checks: these prove only the behaviour they cover. Passing tests are evidence, not a guarantee.
  • Retries: the agent is adapting to a failed action, but repeated retries can also mean it has the wrong model of the problem.
  • Context summaries: the runtime is preserving active state while dropping detail. Useful, but not lossless.

The important habit is to read those steps as signals. File reads and plans are not wasted time if they reduce guessing. A permission prompt is not an annoyance if it prevents an unsafe action. A confident final answer is not enough if the diff, tests, or evidence do not support it.

Optional deep dive A realistic loop-by-loop agent trace. 
Goal:
Fix a bug where a settings page saves a value but does not show it after refresh.

Loop 1:
Observe: read the task, project instructions, and the failing behaviour.
Reason: this sounds like a save-or-load path, not a styling issue.
Act: search for the settings page, request handler, and storage code.

Loop 2:
Observe: find the form submits the right field name.
Reason: the problem is probably after submission.
Act: inspect the server handler and the saved settings model.

Loop 3:
Observe: the handler saves the new value, but the page reload reads an older field.
Reason: the write path and read path use different property names.
Act: update the read path to use the saved property.

Loop 4:
Observe: no test covers saving and reloading this setting.
Reason: add a narrow regression test at the page or service boundary.
Act: write a test that saves the setting and expects it after refresh.

Loop 5:
Observe: test fails.
Reason: the test now proves the current bug.
Act: apply the fix and rerun the targeted test.
Small questions Things I wondered about agents but did not ask at first.

Some agent questions feel too small to ask, but they are useful because they reveal how the system really behaves.

  • Do spelling mistakes in prompts matter? Usually not much if the intent is clear. They can matter when the typo changes a name, command, file path, option, or technical term the agent needs to match exactly.
  • Does being polite help? Politeness does not magically improve the model, but clear, calm instructions often do. "Please keep this scoped to one file and run the narrow test" is useful because it is specific, not because it is polite.
  • Does a longer prompt always work better? No. Long prompts can help when they add constraints, examples, and context. They hurt when they bury the actual task under noise.
  • Why does the agent sometimes sound confident when it is wrong? The model is generating the most plausible continuation from its context. Confidence in the wording is not the same as evidence from files, tools, tests, or logs.
  • Why does asking twice give a different answer? Model calls can involve sampling, and the surrounding context may have changed. Treat repeated answers as more evidence to inspect, not as proof by repetition.
  • Should I paste everything or let the agent inspect files? For code tasks, I prefer giving the goal and letting the agent inspect the relevant files. Pasted snippets are useful, but they can hide nearby code that explains the real problem.
Part 2

How to work with agents safely

Once the mechanics are clearer, the practical question becomes: how do I use this without creating a mess? My answer is narrower scope, clearer verification, and human judgement at the points where judgement matters.

Give the agent a contract, not a vibe

For day-to-day software work, I do not want an agent to sprint off and make a large unreviewed change. I want a small contract:

  1. Understand the task: read the relevant files and restate the goal.
  2. Plan the smallest change: identify the responsible module and expected files.
  3. Edit carefully: touch the fewest files needed.
  4. Verify: run the most relevant tests or checks.
  5. Explain: summarise what changed, why, and what risk remains.

A vague prompt says:

Can you fix this bug?

A useful prompt contract gives the agent edges: what to do, where to work, what constraints matter, and how the result should be checked.

A practical operator playbook

The way you use an agent matters as much as the prompt. I try to run the session in small, reviewable phases:

  1. Start with the outcome: describe the behaviour you want, the bug you see, or the decision you need.
  2. Name the boundary: tell the agent what area to inspect first and what it should avoid changing.
  3. Ask for a short plan before edits: the plan should name likely files, risk, and verification.
  4. Interrupt broad work early: if the agent starts touching unrelated files, stop and narrow the task.
  5. Ask for evidence, not confidence: tests run, screenshots captured, docs checked, or commands executed.
  6. Review the diff yourself: make sure the changed files match the goal.
  7. Make the final answer concrete: what changed, why, what proved it, and what risk remains.

Useful stop signals are broad refactors you did not ask for, repeated failed commands, vague explanations, missing tests for a bug fix, or a final answer that sounds stronger than the evidence. When that happens, I would rather pause and reframe than let the agent continue building on a weak assumption.

Optional deep dive A concrete prompt contract example. 
Task:
Fix the bug where the settings page saves a value but shows the old value after refresh.

Scope:
Start with the settings page, its request handler, and the settings storage service.
Only edit the smallest set of files needed for this behaviour.

Constraints:
- Preserve the current public route and form fields unless the bug requires otherwise.
- Follow the existing validation and persistence patterns.
- Do not refactor unrelated settings or shared infrastructure.
- Add or update a regression test that fails before the fix.

Definition of done:
- Saving the setting and refreshing the page shows the new value.
- Existing settings still load correctly.
- The targeted regression test passes.
- Any broader affected tests have been run or called out.

Before editing:
Summarise your planned changes in 5 bullets.

Reusable instructions help, but only if they stay focused

One part of the video that resonated with me was the idea of standardising agent workflows through skills or reusable instruction files. I already see the value of this in my own repo. An AGENTS.md file can tell agents how to work here: read the architecture map, keep edits small, avoid generated directories, add tests for bug fixes, and run the right checks.

The bigger pattern is simple:

  • Put stable project rules in files.
  • Keep task prompts focused on the current goal.
  • Use skills or manuals for specialised workflows.
  • Let the agent load detailed instructions only when they are relevant.

This helps with context too. A giant prompt can become noisy. Smaller reusable instructions are easier to maintain, easier to review, and less likely to bury the important task-specific detail.

Optional deep dive Self-correcting rules, treated carefully.

A lightweight version of self-correcting instructions could be useful:

# Learned Rules
1. Tests: when fixing a user-visible bug, add a regression test at the narrowest useful layer.
2. Sources: when summarising external material, link the source and avoid copying long passages.
3. Scope: before editing, identify the smallest module responsible for the behaviour.

The safe version is that the agent may propose a new rule after a real correction or failure, but the human reviews it before it becomes permanent. Otherwise, instruction files can slowly fill with outdated preferences and misunderstood lessons.

Use multiple agents only when independence helps

Multi-agent workflows can be useful, but I would not reach for them by default. For most normal tasks, one well-constrained agent plus good tests is enough.

In practice, using multiple agents can be as simple as running separate sessions with different roles. One agent implements the change. Another reviews the diff. A third might read documentation, check security assumptions, or look at performance. They do not need to talk to each other directly for the pattern to be useful; the value is that each pass starts from a different brief.

The reason to do this is independence. If one agent makes an early bad assumption, a second agent with a review-only brief is more likely to challenge it than an agent continuing its own work. Multiple agents help most when the jobs are genuinely different: build, review, research, test, security, UX, or performance.

Practical comparison One visible agent, internal sub-agents, or separate sessions.

There are a few different things people mean by "multiple agents":

  • One visible agent session: this is one continuous conversation and one main loop. You can ask it to implement, then review its own diff, but it still carries the same context and may keep the same assumptions.
  • Internally orchestrated sub-agents: a CLI or platform might spawn several workers behind the scenes, such as one for code search, one for documentation, and one for review. This can be efficient, but the real independence depends on how separate their prompts, context, and tools are.
  • Separate agent sessions: running three terminals, IDE windows, or branches gives you more manual independence. Each agent can get a different brief. The trade-off is coordination: if they all edit the same files, you can create conflicts or duplicated work.

The useful question is not "how many agents are running?" It is "are they bringing different evidence or judgement?" Three agents repeating the same prompt against the same context may just produce more text. A builder, a reviewer, and a researcher with separate briefs can be much more useful.

If I did use multiple agents, I would keep the workflow simple:

  1. Give each agent a separate job: implementation, review, research, security, performance, or UX. Do not ask everyone to do everything.
  2. Give them the same goal and constraints: otherwise disagreement may come from different assumptions, not useful judgement.
  3. Ask for short outputs: findings, risks, recommendation, and evidence. Avoid long transcripts.
  4. Compare disagreement explicitly: if agents disagree, make the disagreement the thing to inspect.
  5. Keep one final owner: one person or one final synthesis step decides what actually changes.

The useful patterns are:

  • Doer and reviewer: one agent implements, another reviews the diff for bugs and missing tests.
  • Specialist review: one pass for security, another for performance, another for UX or accessibility.
  • Consensus: several agents independently assess a risky decision, and disagreement becomes a signal.
  • Research split: separate investigations into docs, code, and runtime logs before one final synthesis.

The risk is that orchestration can look impressive while adding noise. More agents does not automatically mean better judgement. It can just mean more text, more disagreement, and more cost.

Optional deep dive What a useful multi-agent output should look like.

The output I would want from a multi-agent discussion is not a long transcript. It is a decision record:

Decision:
Use the small controller-level fix instead of refactoring the whole agent runtime.

Why:
- Fixes the reported bug directly.
- Lower blast radius.
- Can be covered with one regression test.
- Keeps the public route and request model stable.

What the agents contributed:
- Implementation agent found the failing controller path and proposed a fix.
- Reviewer agent rejected a broader service extraction as unnecessary for this bug.
- Performance reviewer found no evidence that this path is currently hot.

Follow-up:
- Add a metric before optimising this path.
- Revisit extraction if another feature needs the same logic.

The failure mode I watch for

The failure mode that worries me most is not one bad answer. It is a bad early assumption that survives for too long. This can send you down a rabbit hole, especially if the task sits outside your own experience and you are more likely to accept what the agent suggests.

An agent can misread a requirement, pick the wrong file, or misunderstand a failing test. If nothing interrupts that, it can spend the next chunk of work confidently building on top of the mistake. The conversation then fills with its own previous reasoning, and the story starts to feel more coherent than the evidence actually is.

This is why I like short plans, targeted tests, and validator loops. They create natural interruption points.

The doer-validator pattern is one of the most practical agent patterns for software work:

Doer:
- read context
- make the edit
- run a first check
- explain the change

Validator:
- inspect the diff
- check scope
- run or request tests
- look for missing regression coverage
- reject weak explanations

This does not have to mean two separate AI tools. Sometimes it is the same agent in a different mode: first implement, then review the diff like a strict reviewer. True independence is stronger, but even a deliberate second pass is better than no review step.

Practical checklist

Before trusting an agent's change, I want these answered

  • What exact behaviour changed?
  • Which files were touched and why?
  • What test would fail without this change?
  • What command proved the change works?
  • What assumption is still unverified?
  • What is the blast radius if this is wrong?

Context is an engineering limit, not just a token limit

Agents can burn through a lot of context because every loop adds observations, plans, outputs, errors, and corrections. The issue is not only cost, although cost matters. The issue is that the agent can lose the important signal inside too much history.

Good context management means:

  • Give the agent the files it needs, not the whole world.
  • Keep tool output focused.
  • Summarise old investigation steps when they are no longer active.
  • Keep the current goal and definition of done visible.
  • Do not let stale assumptions hang around unchallenged.
Optional deep dive Context compression and cost change the design.

A bad compression says:

We investigated the issue and made some progress.

A useful compression preserves state:

Goal:
Fix a settings page bug where saved preferences reset after refresh.

Known files:
- The settings form posts to SavePreferences.
- Preferences are read back through the user settings service.

Completed:
- Confirmed the form submits the new value.
- Found the save path writes the correct field.
- Found the read path still maps the old field name.

Verification still needed:
- Add a regression test for save then refresh.
- Run the targeted settings tests.

Cost follows the same pattern. Not every step needs the strongest model. Cheap models may be fine for summarising logs or repetitive transformations. Stronger models make more sense for architecture decisions, security-sensitive review, and ambiguous trade-offs. Deterministic tools should handle tests, parsing, linting, and policy checks.

Start with low-risk autonomy

If I was advising someone who had only used normal chat tools, I would not start with five agents, browser automation, MCP servers, and complex orchestration. I would start with safe tasks: documentation cleanup, a small test, or a narrow refactor.

I am comfortable spending more time around levels 2 and 3. Level 4 is interesting for research-heavy or high-volume work. Level 5 is where I want serious policy, observability, approvals, and audit logs before I would trust it.

My current boundaries are:

  • Low-risk: formatting, small docs changes, simple tests, straightforward HTML edits.
  • Medium-risk: application logic, refactors, controller or service changes. I want a plan, narrow scope, and tests.
  • High-risk: auth, payments, data deletion, deployment, secrets, production config. I want explicit approvals and stricter review.
  • Very high-risk: broad filesystem access, destructive commands, production writes. I want policy enforcement, audit logs, and usually manual execution.
Starter prompt A practical first agent prompt for a codebase task. 
You are helping me make a small, safe change in this repo.

Task:
[describe the change]

Before editing:
1. Read the project instructions.
2. Find the smallest responsible module.
3. Tell me the files you expect to touch and why.

Constraints:
- Keep the change scoped to this behaviour only.
- Prefer existing patterns.
- Do not edit generated folders.
- If this is a bug fix, add or update a regression test.

Verification:
- Run the narrowest relevant test first.
- Tell me exactly what passed or what could not be run.

Final response:
- What changed.
- Why this approach.
- What test proves it.
- Any remaining risk.

What agents are good and bad at right now

In my experience, agents are strongest when the task has a clear feedback loop:

  • Fix this test.
  • Refactor this small area without changing behaviour.
  • Add validation and cover it with a unit test.
  • Read these docs and summarise the implementation path.
  • Generate a first draft, then let me edit it.
  • Compare two approaches and surface the trade-offs.

They are weaker when the task depends on hidden context, team politics, product judgement, unclear ownership, or subtle production risk. They can overfit to the immediate context, create plausible explanations after the fact, miss the file they did not inspect, and make broad changes look normal unless you force them to account for each touched file.

The practical stack I would aim for

If I was designing a serious agent workflow for a team, I would want this stack:

  • Project instructions: coding standards, testing policy, ownership boundaries, generated-folder exclusions.
  • Tool registry: clear tools with schemas, permissions, and predictable outputs.
  • Approval policy: low-risk actions run automatically, high-risk actions require explicit approval.
  • Audit log: record commands, file edits, external calls, approvals, and failures.
  • Verification: tests, linters, policy checks, screenshots, or smoke tests depending on the work.
  • Review mode: a second pass focused on bugs, missing tests, and blast radius.
  • Context hygiene: summaries that preserve active state and drop stale noise.
  • Cost controls: avoid using expensive reasoning for cheap mechanical steps.

Most of that is normal engineering discipline applied to agents. The model is new. The need for clear contracts, tests, logs, permissions, and review is not.

What I am taking from all this

The main thing I am taking from the video and from my own use is that agents are best understood as work loops, not answer machines.

The model matters, but the surrounding system matters just as much: what it can observe, what tools it can call, what rules it follows, what checks run before the work is trusted, and what the human still owns.

That last question is the big one for me. The agent can do more of the mechanical work now, but I still need to own the judgement. I need to understand the change, know the failure mode, and be able to defend the result.

For now, my practical rule is simple: give agents useful tools, narrow goals, clear constraints, and real verification. That is where they start to feel less like a clever chatbot and more like a useful engineering system.
