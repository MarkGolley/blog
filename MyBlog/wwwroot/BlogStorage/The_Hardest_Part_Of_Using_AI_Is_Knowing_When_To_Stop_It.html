How to keep a coding agent on scope—and recognise when to interrupt.

One of the most useful things about coding agents is that they can keep working. They inspect the code, make a change, run a test, investigate a failure, and try again.

That is also one of the most frustrating things about them.

You ask for a small fix. The agent notices something nearby that could be improved. That improvement leads to a refactor. The refactor affects another component. Before long, the original problem is buried inside a much larger set of changes.

Each step can sound reasonable on its own. Taken together, they can leave you wondering why a simple request has turned into an afternoon of reviewing code.

I’m increasingly convinced that using agents well requires more than explaining what you want them to start doing. You also need to make it clear what finishing looks like—and recognise when the work has stopped moving towards it.

How a small task gets bigger

Take a hypothetical example: a form shows the wrong validation message.

You ask the agent to fix it. While investigating, it notices duplicated validation logic. It extracts a shared helper. Then it updates another form to use that helper. Some tests need changing, and an inconsistency in error handling becomes visible.

Now the agent is standardising error handling.

The original request was a validation message.

The other changes might have value, but they create extra decisions, extra review, and extra opportunities to break something. They also make it harder to answer a basic question: which part of this diff actually fixes the problem?

This is how scope drift can happen without one obviously terrible decision. A series of plausible improvements gradually changes the task.

Finding more work does not automatically make it part of the current work.

“Fix this” leaves a lot unsaid

When I give another developer a task, there is usually some shared context. They may know the release deadline, the conventions of the team, or that this particular component is being replaced next month.

An agent may not have any of that context unless it is provided or discovers it.

“Fix this form” leaves several questions open:

  • Is the problem the message, the validation rule, or the whole interaction?
  • Should similar forms change too?
  • Is a refactor acceptable?
  • What evidence would show that the fix is complete?

A useful task description does not need to become a specification document. A few clear sentences can remove a surprising amount of ambiguity.

For the form example:

Fix the incorrect validation message when the email field is empty. Preserve the existing validation rules and other form behaviour. Add or update a focused regression test, then run the relevant tests. Leave unrelated cleanup for a separate task.

That gives the agent an outcome, a boundary, and a finish line.

Give the agent room inside the boundary

There is a balance here. I do not want an agent asking permission to read a file, choose a variable name, or run a relevant test.

Constant interruptions make delegation feel like operating the tool manually.

The distinction I find useful is between implementation decisions and scope decisions.

An implementation decision is choosing how to achieve the agreed outcome within the existing constraints. A scope decision changes what is being delivered, what behaviour is affected, or how much of the system needs to change.

For example, finding the right place to correct a validation message is part of the task. Deciding to replace validation across the application expands it.

Sometimes a broader change really is necessary. The apparent message bug might come from a shared rule used by several forms. In that case, the agent should explain the dependency and why a narrow fix would be insufficient.

That is a worthwhile interruption because there is a meaningful decision to make.

Ask what the next step contributes

The question I want an agent to be able to answer throughout a task is:

How does your next action help complete the original request?

“Updating this test proves that the empty email case now shows the correct message” is a clear answer.

“Improving consistency across the application” needs more scrutiny if consistency was never part of the request.

This is also useful when a task gets stuck. An agent can remain busy while making very little progress. It can repeatedly adjust code, rerun checks, and produce explanations without resolving the assumption that caused the problem.

Activity alone is weak evidence that the approach is working.

After repeated failed attempts, I want a pause to reconsider:

  • What has actually been established?
  • Which assumption is still unverified?
  • What new information would the next attempt provide?

A retry based on new evidence is different from another variation of the same guess.

When I would interrupt

I would not use a fixed number of tool calls or changed files as the stopping rule. Some small-looking problems genuinely need investigation across several layers.

Instead, I would watch for changes in the direction of the work.

The agent starts solving adjacent problems.
It notices a naming inconsistency or an unrelated bug and quietly adds it to the task. Those findings can be recorded without being implemented immediately.

The explanation no longer matches the request.
The task was a specific bug fix, but progress updates now describe a wider redesign. That is a good point to re-establish the intended outcome.

The same failure keeps returning.
Repeated attempts are producing more code without a clearer diagnosis. The next useful step may be inspection, a smaller reproduction, or input from someone who knows the system.

Tests are being weakened to make the change pass.
A failing test can reveal an outdated expectation, but it can also reveal that the implementation is wrong. Changing the expectation needs a reason tied to the intended behaviour.

The task appears complete, but optional work continues.
The requested behaviour works and the relevant checks pass. The agent then proposes another abstraction, more cleanup, or additional features. That is usually a good place to finish and separate any follow-up work.

What to do when it has already drifted

Once a task has expanded, it is tempting to let the agent finish because it has already invested effort.

But every extra change still has to justify its place in the result.

A useful recovery instruction is:

Pause editing. Summarise the original request, what you have changed, and what remains necessary to complete it. Identify changes that fall outside that scope. Do not revert anything yet.

That last sentence matters. A rushed cleanup can remove useful work or interfere with changes that were already present.

First inspect the state. Then decide what to keep, what to separate, and what to undo.

If the approach itself has become confused, continuing from the latest explanation may preserve the confusion. Restating the task from the actual code and observed behaviour can be more useful than adding another layer of instructions.

A scope prompt you can reuse

This is the kind of brief I would use as a starting point:

Outcome:
[Describe the specific behaviour or deliverable I want.]

Boundaries:
Keep changes limited to what this outcome requires.
Preserve unrelated behaviour.
Record unrelated bugs and cleanup opportunities separately.

Autonomy:
Make routine implementation decisions within this scope.
If a broader change is necessary, explain the dependency
and proposed expansion before proceeding.

Verification:
Use [relevant tests or checks] to verify the outcome.
If a check fails, investigate the cause before changing
the expected behaviour.

Stop condition:
Once the outcome is achieved and the relevant checks pass,
stop. Summarise what changed, how it was verified, and
any remaining limitations.

I would shorten this for a trivial task. The useful part is the clarity about what success requires.

It is also worth remembering that instructions are not enforcement. An agent can misunderstand a boundary or incorrectly decide that an extra change is necessary. Reviewing the diff and checking the evidence still matter.

Finishing is part of the task

In my earlier writing about AI and learning, I discussed the risk of shipping code faster than your understanding develops. Scope drift adds another version of that problem: the amount of work to review grows beyond the decision you originally intended to make.

A good result should be understandable. You should be able to explain what changed, why it was needed, and what proves it works.

The agent’s ability to continue is valuable when the next step contributes to that result. Once it starts creating a different task, persistence becomes something you have to manage.

Before starting, define the finish line. During the work, check that the next action still points towards it. And when the requested outcome is achieved, let the task be finished.
