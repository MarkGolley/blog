Choosing between Astra and Sol - and when to use ChatGPT desktop or your IDE.

The newer models are impressive. The speed at which I can get through my allowance is rather less impressive. That has made me think more carefully about how I use my GPT Plus membership. It is tempting to select the most capable model, turn up the reasoning, and leave it there. If a better model is available, why wouldn't I use it?

Then I hit a limit halfway through something useful. Suddenly, choosing the strongest model for every little job does not seem quite so sensible.

So this is what I wanted to work out: how do I get more useful work from the membership I already pay for?

What am I actually using up?

I keep thinking of it as “burning tokens”, but that needs a bit of explanation.

Tokens are small chunks of information the model reads and writes. Your question counts, but so do files, earlier messages and results from tools. The reply you see is only part of it. Your allowance also depends on the model and how it does the work. OpenAI explains the usage rules here.

Imagine asking: “Why is this test failing?” That is one short message. But the agent might read five files, run the test, inspect the error and try a different approach. There is quite a lot going on behind that one question.

So hitting a limit sooner does not, by itself, prove that a newer model writes more tokens. And asking for a shorter answer will not fix an agent spending ages investigating the wrong thing.

Does every task deserve Astra?

OpenAI describes Astra as the choice for harder problems, and Sol as a good everyday model for writing and coding. That seems a useful place to start, rather than automatically picking the biggest option. Here is its model guide.

Here is the approach I start with:

  • I know what needs doing: start with Sol. Fix a small bug, add a straightforward feature or tidy up a draft.
  • I cannot work out what is going wrong: consider Astra. A bug that crosses several parts of the application is a better reason to use it than changing a button label.
  • It is a simple, repetitive job: consider Luna. There are smaller options too.

The reasoning setting matters as well. Think of it as how much effort you ask the model to spend working through the problem. I would not turn it up to maximum for every task. OpenAI's guide recommends trying settings and keeping the lighter option when it does the job well.

Of course, repeatedly telling Sol to “try again” is not necessarily saving anything. If Astra solves the problem with fewer attempts, it could be the better choice overall. I put together a small shopping-list experiment below to start testing this. As it turned out, none of the models needed a second attempt on that task.

Before switching, though, check what you have given it. Did you include the actual error? Does it know what the code is supposed to do? A stronger model still needs the right information.

Check which Sol you actually mean

There is another small catch: GPT-5.6 Sol and GPT-6 Sol are different versions with different published rates. Just saying “I used Sol” leaves out something useful.

For the same amount and type of tokens at Standard speed, the published credit rate for GPT-6 Astra is five times GPT-6 Sol's rate. That does not mean your Plus allowance will last exactly five times longer with Sol. Credit pricing and included subscription limits are different things. The current rates are listed here.

Check the full model name in the picker, especially when following advice written a few months ago.

ChatGPT desktop or the IDE?

By IDE, I mean the editor where I write and run my code, such as Rider or VS Code.

I would start in ChatGPT desktop when I want to talk an idea through, compare options or work with documents. The app can also work with files, projects and other tools, so it is useful for more than chatting. More about the desktop app.

Once I need help with the actual code, the IDE often makes more sense. I can point the agent at an open file or selected code and review its changes alongside it. That is what the Codex IDE integration is designed to support.

For example, I could use ChatGPT to discuss whether AislePilot should reuse a saved meal plan instead of generating one again. When it comes to changing that behaviour, I want the agent looking at how my app actually works. Otherwise we could spend a lot of time discussing a solution that does not fit.

There is overlap. Desktop can change code too, and the IDE can help explain an idea. I would use whichever makes the job easier to follow.

One thing to be clear about: switching apps does not give you a fresh allowance. ChatGPT Work and Codex share usage. Regular Chat is a separate mode, so check which one you are using and the limits shown in your account. More about shared usage.

Do not make it start from scratch

If I move from discussing an idea in ChatGPT to building it in the IDE, I want to take the useful decisions with me. A short note is usually easier to follow than a whole conversation:

Fix the message shown when the email field is empty.
It should tell the user to enter an email address.
Keep the other validation rules as they are.
Check whether the message comes from the browser or server.
Add a test for this case and run the relevant existing tests.

That says what I want, what should stay the same and how to check it worked.

For a task already in progress, I would keep the conversation going while its history is useful. For something unrelated, I would start a new one. There is little benefit in carrying a long discussion about meal planning into a completely different bug fix.

The easiest work to save is work I never needed

If I ask for a bug fix and the agent starts rebuilding half the feature, I want to know why. It might have a good reason. It might also have found extra work that can wait.

The same applies when it gets stuck. Before another attempt, ask what it has learned and what it will try differently. Watching it make the same mistake again is frustrating enough without using more of the allowance.

A prompt I would use is:

Keep this focused on the change I asked for. Make a note of unrelated improvements for later. If you get stuck, explain what you have learned and what you will try next. Once it works and the relevant checks pass, stop and tell me what changed.

This is not a magic token-saving prompt. It is a way to avoid paying for work I did not need in the first place.

I gave both models the same broken shopping list

I used a small Python function inspired by AislePilot. Its job was to combine ingredients: 500 g of rice plus 1 kg should become 1,500 g. Two tomatoes and 500 g of tomatoes should stay separate. The starting code got those cases wrong.

I compared Sol Low, Astra Low and Sol High, with three fresh trials each. Every trial received the same instructions and starting function. A fixed set of 14 checks covered units, names, sorting, rounding and leaving the input unchanged. Each model could submit up to three fixes, receiving the same kind of test feedback after a failure.

This was a small API code-fixing exercise, not an IDE session or a measurement of Plus limits. The models had no browsing or file tools. Requests ran one at a time, with the order rotated between rounds. All nine results are below.

  • gpt-6-sol / low: 3/3 passed; median 840 tokens and $0.00478 per trial.
  • gpt-6-astra / low: 3/3 passed; median 827 tokens and $0.02327 per trial.
  • gpt-6-sol / high: 3/3 passed; median 1,264 tokens and $0.00902 per trial.

Median means the middle result of the three trials, so one unusually large or small run does not set the headline number.

Every model passed on its first attempt. Sol Low was enough for this problem. Astra Low used a similar number of tokens, but cost more at its higher rate. Sol High used more tokens without improving the test result.

That supports starting with a lower setting for a small, clearly explained job. It does not show whether Astra saves retries on harder work, because none of these valid trials needed a retry.

How much can this tell us?


Three trials on one small problem are a useful example, not a verdict on either model. Passing these checks does not prove the code is right for every possible input. A harder task could give a different result.


I also caught a mistake in my own test runner during an initial pilot: it rejected valid Python list operations. I fixed it, added a regression check and restarted every condition. That invalid pilot is kept in the experiment folder and excluded from these results.


The API reports reasoning usage separately within output tokens. Prices came from the Sol and Astra model pages. The downloadable record includes exact model IDs, settings, all submitted fixes and test feedback.




What I would change first


Start with Sol for everyday jobs. Give Astra the harder problems. Use ChatGPT desktop to talk things through, and bring the work into the IDE when having the code in front of you helps.


As I wrote in my post about AI and learning, I still need to understand what has been done. A confident answer is not enough.


I want to finish something useful, understand it, and still have some allowance left to carry on. That feels like a better use of Plus than leaving everything on the strongest setting and hoping for the best.
